# AGENTS.md — Enveo

## What this is
**Enveo** is a private, local-first envelope budgeting app (YNAB-style, zero-based), built as a mobile-first PWA with optional end-to-end encrypted sync and AI-assisted workflows. Amounts live in minor units, balances are derived from the ledger, and the client is the source of truth — the server is a sync and convenience layer.

## Stack & layout
Monorepo with bun workspaces (`packages/*`):
- **packages/shared** (`@enveo/shared`) — pure domain, zero I/O: `budget.ts` (ledger math), `applyOp.ts` (mutation reducers for the client replica), `stateResponse.ts`/`summary.ts`, `ops.ts` (zod op schemas), `aiBudget.ts` (budget suggestion engine), `aiPrompts.ts` (ALL AI prompt builders/parsers). This is the shared math for client and server — parity is guaranteed by running identical code on both sides.
- **packages/api** — bun + Hono + Drizzle + Postgres 16. `src/index.ts` mounts routes under `/api`; in production it also serves the built web app (SPA fallback). Migrations in `drizzle/` run on container start; the migrator orders by timestamp from `meta/_journal.json` — semantic changes always require a NEW migration file.
- **packages/web** — React 18 + Vite + TanStack Query, PWA (`vite-plugin-pwa`, registerType `prompt`). Local-first lives in `src/lib`: `store.ts`/`idb.ts` (ledger replica in IndexedDB), `outbox.ts`/`persist.ts`, `sync.ts` (push/pull/snapshot/replace), `mutate.ts` (`local.*` → applyOp + outbox), `version.ts`. i18n lives in `src/lib/i18n/` (runtime + `registry.ts` + one file per locale; see § Conventions).

## Running locally
`bun` must be on PATH. Full stack via Docker:
1. `cp .env.example .env` and set `POSTGRES_PASSWORD` + `BETTER_AUTH_SECRET` (required — `openssl rand -hex 32`; `scripts/deploy.sh` generates both). Optionally `OPENAI_API_KEY` + `OPENAI_MODEL` for AI features.
2. `make up` (build + start; migrations run automatically). A fresh install has NO user and NO budget: the first visit creates the owner account, the first API call lazily creates an EMPTY budget, and the in-app onboarding wizard does the initial setup. `make logs`, `make down`.
3. Dev without Docker: `docker compose up -d db`, then run migrations with `DATABASE_URL` set, then `make dev-api` (API) + `make dev-web` (Vite). Vite listens on `::1` — open `localhost`, not `127.0.0.1`.

### The runtime image (do NOT re-fatten it)
- **ONE Bun version, everywhere.** `.bun-version` is the source of truth; CI, the weekly audit workflow, `@types/bun`, the docs and EVERY Docker stage must agree, and `scripts/lib/bunVersion.test.ts` fails `bun run test` when they drift. Each base is pinned to the exact version AND its multi-arch manifest digest (`oven/bun:<v>[-variant]@sha256:<d>`) — a bare tag is rejected, and so are two stages on the SAME variant with different digests. A Bun bump moves version + BOTH digests + `@types/bun` + lockfile in ONE reviewed PR.
- **Three stages, TWO bases.** `build` on **Debian** (`oven/bun:<v>`; full frozen install — Vite's native glibc toolchain lives here and never leaves) → `deps` and `runtime` on **Alpine** (`oven/bun:<v>-alpine`): an explicit ALLOWLIST of manifests, the closure, `packages/api/src`, `packages/shared/src`, the whole `packages/api/drizzle` tree, built `packages/web/dist`. Never `COPY --from=build /app /app` again, and never add a directory "just in case".
- **Why Alpine may run what Debian built** — one checked property, not a hope: the production closure is 26 packages of PURE JAVASCRIPT with **zero native binaries**, so nothing glibc-linked crosses the boundary. `image-inventory` sweeps every file under `/app` for ELF magic and FAILS on any hit; if a future dependency pulls in a `.node` addon this breaks loudly instead of at some untested `require()`. Bun bundles its own ICU (75.1 on both images), so Intl is byte-identical on musl — currency digits, CLDR plural categories and `Intl.DisplayNames` were compared directly and the shared/web suites pass on the Alpine runtime. Money formatting is browser-side anyway; the server's only `Intl` use is `DisplayNames` in `aiPrompts.ts`. `deps` runs on the RUNTIME base so the shipped tree is the one that platform resolved.
- **`bun install --production --frozen-lockfile --filter` is NOT enough on its own.** Bun materialises every OPTIONAL PEER resolvable in the workspace graph, and better-auth declares react, react-dom, drizzle-kit, prisma, mongodb and vitest as optional peers — so a "production" install still contains drizzle-kit, tsx and three esbuilds (that is 3 CRITICAL + 32 HIGH scanner findings, all in a build tool). `scripts/prune-runtime-deps.ts` walks the REQUIRED-link graph (`dependencies` + `optionalDependencies` + non-optional peers) and deletes the rest; rules are pure in `scripts/lib/runtimeClosure.ts`. `drizzle-orm` is one of those optional peers but a direct `@enveo/api` dependency, so it is kept. The prune FAILS THE BUILD if the closure loses a package the API imports.
- **Alpine has no `bash` and no `curl`** — busybox `sh` and `wget` only. The entrypoint is POSIX `sh`, and the compose healthcheck uses `bun -e fetch(...)`, which needs neither. Do NOT `apk add` a convenience tool to fix a script: every ADDED package is new CVE surface, and the whole point of the base is that it has almost none. That rule is about **adding software**; it has never forbidden **patching what is already there** — see the next bullet, and do not read the two as the same thing.
- **`apk upgrade --no-cache` in `deps` and `runtime` is deliberate, and installs NOTHING new.** It moves the packages the base already ships to the current patch level of the Alpine branch the pinned digest is built on; the base stays digest-pinned. It exists because Alpine 3.22.4 inside `oven/bun:1.3.14-alpine` ships openssl 3.5.6-r0 with **CVE-2026-45447** (HIGH, heap use-after-free in `PKCS7_verify()`): `image:scan` fails closed on HIGH and critical/high have NO exception path, so it had to be FIXED — `security/image-scan-ignore.yaml` stays empty. Upstream has not rebuilt on a patched Alpine and 1.3.14 is the newest Bun, so re-pinning the base was not an option. The upgrade also refreshes `ca-certificates-bundle`, `apk-tools`/`libapk2` and `alpine-release` (3.22.4 → 3.22.5); it costs ~2.7 MB, because a package upgrade writes new copies in a new layer while the originals stay in the base layer.
  - **NOT version-pinned, on purpose.** Alpine's repository keeps only the CURRENT build of a package per branch, so `libcrypto3=3.5.7-r0` would break every build the day 3.5.8-r0 lands and the old build leaves the mirror — release-blocking on Alpine's schedule, for a package upgraded precisely to stay current. **The security property is enforced by the SCAN, not by a pin**: still-vulnerable current builds fail `image:scan` and stop the release. Do not "harden" this by adding a version back. The consequence — two builds of the same commit can differ in OS patch level — is already true (Vite injects a build time), and §3d handles it by promoting aliases **by digest**, never by rebuilding. `image-inventory` records the installed OS package set as a FACT (printed, not judged) so the drift is legible.
  - **The vulnerable code was never LOADED here** — worth knowing before panicking, and before dropping this line later: Bun statically bundles BoringSSL, so `ldd /usr/local/bin/bun` reports only musl, libstdc++ and libgcc. The only binaries in the image linking libssl/libcrypto are `apk` itself, busybox's `ssl_client` and the OpenSSL engines, and none of them run — the entrypoint `exec`s bun and the healthcheck is `bun -e fetch(...)`. Reachability is why this was not an emergency; policy is why it was fixed anyway. When upstream rebuilds on a patched Alpine, re-pin the base digest and DROP the upgrade.
- **Unprivileged and signal-correct.** Files stay root-owned, the container runs as the image's `bun` user (uid 1000 on both variants) — `/app` is not writable by the app. `scripts/docker-entrypoint.sh` keeps migrate→start with `set -eu` (a failed migration must prevent the API from starting) and `exec`s Bun so it receives SIGTERM; without `exec` the shell absorbs it and every stop ends in SIGKILL after the full grace period (the old image: 30s + 137; now: 0.6s + 143).
- **Compose ships hardened**: `init`, `cap_drop: ALL`, `no-new-privileges`, `read_only` root filesystem with tmpfs `/tmp` as the ONLY writable path. Enveo writes no files — data is in Postgres. Do not "fix" a permission error by widening this.
- **The build context has no `.git`**, so the release identity is PASSED IN: `--build-arg SOURCE_COMMIT` → the web build stamp (`__BUILD_INFO__.sha`) AND the OCI `org.opencontainers.image.revision` label, which must match. Absent, it degrades to a timestamp-only stamp.
- **A test-only module inside a shipped `src/` tree carries `.test` in its BASENAME** — `*.test.ts` (suites), `*.test-support.ts` (helpers), `*.test-child.ts` (processes DB tests spawn). One glob then covers all of them in `.dockerignore` and one rule in the inventory. Do NOT invent a fourth spelling: `test-helpers.ts`, `testSupport.ts` and five `*-child.ts` DB drivers matched nothing and SHIPPED — including a helper importing `fast-check`, which the production prune removes, so users received a module that could never load, and a child that wipes a budget's rows. The name rule is backed by a name-INDEPENDENT check: the inventory resolves every import of every shipped module inside the image and fails on any that cannot resolve.
- **Prove it, don't eyeball it**: `bun run image:inventory <ref> [--sha <commit>]` checks the allowlist, the absence of named dev packages, that every shipped module's imports resolve, that no ELF binary is present, that the image's own `bun --version` equals `.bun-version` (this is what binds the pinned DIGEST to the version its tag claims — every other check is text vs. text), non-root/read-only and the metadata, all against a BUILT image (rules unit-tested in `scripts/lib/imageInventory.ts`); `bun run image:scan <ref>` runs a digest-pinned Trivy over OS + application layers and fails closed (no `--ignore-unfixed`, no severity threshold; exceptions are exact and EXPIRING in `security/image-scan-ignore.yaml`). Both need a built image, so they are outside `verify`/`verify:ci`; CI's docker job runs the inventory.

### The release pipeline (a tag is a REQUEST to publish, not an authorisation)
- **Four ordered jobs, permissions granted per job** (`release.yml`): `validate` (`contents: read`) → `verify` (`contents: read`) → `publish` (`packages`/`id-token`/`attestations: write`) → `github-release` (`contents: write`). Workflow-level `permissions: {}`. Nothing before `publish` can write anywhere, so a bad tag fails with no registry login having happened. Concurrency is keyed by the resolved tag, `cancel-in-progress: false`.
- **ONE verification gate, called twice.** `verify.yml` is a `workflow_call` workflow running root `verify:ci` against an explicit ref; branch CI and release both call it as `./.github/workflows/verify.yml` (local form — the CALLER's revision runs). Neither keeps a second command list. Release passes the SHA the tag resolved to.
- **Everything downstream uses the RESOLVED tag SHA, never `github.sha`** — on a `workflow_dispatch` that is the default-branch head, and it would land in the OCI revision label AND the in-app build stamp with nothing to catch it (image-inventory compares the two, and both would be equally wrong).
- **The tag policy is tested code, not a shell glob** (`scripts/lib/releaseVersion.ts`): a strict SemVer subset — no build metadata (`+` is not a legal OCI tag character), no leading zeros, no suffix garbage, no ref-like input. The old `case` glob accepted `v3.8.0rc1`, `v3.8.0_final` and `v03.8.0`. Then: the tag EXISTS under `refs/tags/` and dereferences to a commit, that commit is an ancestor of `origin/main`, and `APP_VERSION` read out of the TAGGED commit agrees — byte-for-byte for a stable release; a PRERELEASE may carry the full version or its bare core (`v3.8.0-rc.1` ⇒ `3.8.0` or `3.8.0-rc.1`), so an rc costs no throwaway APP_VERSION commits.
- **The exact SemVer image tag is IMMUTABLE; `latest`/`MAJOR.MINOR` move only by verified digest.** `release-image.ts probe` decides: absent → build; present with matching identity labels → resume from that digest WITHOUT rebuilding; present with a different revision → STOP for investigation; registry error → STOP. That last case is load-bearing — a 401 or a timeout read as "absent" would rebuild over a released tag, and rebuilding is not idempotent (Vite stamps a build time, so the same source yields a different digest). A prerelease publishes only its exact tag and moves nothing.
- **The POST-PUSH scan is the authority; the pre-push one is fast feedback.** Both `image:scan` + `image:inventory` run per architecture, first on locally `--load`ed candidates and then on the artifact PULLED BACK from the registry — before attestation and before any alias move. The second pass is not redundant: the push is a SEPARATE BuildKit invocation linked to the candidates only by a best-effort cache, and the runtime `apk upgrade` is deliberately unpinned, so a cache miss can resolve different OS package builds than Trivy just judged. Scanning only the candidate would let a CRITICAL ship while the log claimed otherwise. The honest guarantee is "nothing unscanned is ever RELEASED": a post-push finding leaves the exact tag pushed but never attested, aliased or released — recover with a new patch version, never by overwriting. Per-arch matters because the prune runs inside the per-arch `deps` stage (CI's single-arch build is no evidence about the arm64 image a Pi/Graviton self-hoster pulls).
- **ONE architecture list: `PLATFORMS`.** Candidate builds, the gate loop and the published-artifact loop all derive from it (the last from the published index). A hardcoded `for arch in amd64 arm64` beside a `platforms:` input is two lists that must agree — adding `linux/arm/v7` to one would publish an architecture no scan ever saw. `scripts/lib/releaseWorkflow.ts` FAILS the suite if any architecture is named anywhere else in the workflow.
- **Aliases only ever move FORWARD.** Before moving one, `release-image.ts alias-plan` reads which version it currently serves and skips it if that is already newer — otherwise a legitimate re-run of an older tag (to finish its missing GitHub Release) silently downgrades every self-hoster pulling `latest`. A skip is reported loudly and is NOT fatal; an alias that does not say what it serves is also skipped, because refusing to move is recoverable and an unnoticed downgrade is not.
- **LABELS AND ANNOTATIONS ARE TWO DIFFERENT OUTPUTS — override BOTH.** `docker/metadata-action` honours a `labels:` override but still derives ANNOTATIONS from `github.sha`, so a release published the correct commit in the image config and the BRANCH HEAD on the manifest; the inventory could not notice, because it reads the config label. Annotations ride on the index/manifest, which is what registries show and what supply-chain tooling reads without pulling the config blob. Set `annotations:` alongside `labels:`, set `DOCKER_METADATA_ANNOTATIONS_LEVELS: manifest,index` (the default annotates manifests only, leaving the index with NO revision at all), and `release-image.ts verify` checks the index and every platform manifest — a source with no annotations is a violation, not "nothing to compare".
- **Pull each platform by its OWN manifest digest.** Two `docker pull --platform` calls against the same INDEX digest fail with `cannot overwrite digest …`: one reference maps to one local image. `release-image.ts platforms` lists `platform<TAB>digest` from the index, so the architectures inventoried are by construction the ones published, and the per-image architecture assertion catches any entry that resolves to a duplicate.
- **Provenance (`mode=max`), SBOM and a GitHub digest attestation are REQUIRED**, verified before the aliases move. The `unknown/unknown` entries this adds to GHCR's package list are attestation referrers, not runnable architectures — filter them, never count them. Artifact attestations need a PUBLIC repo on Free/Pro/Team: while `enveo/enveo` is private the step FAILS, deliberately not conditional and not `continue-on-error`, and the release stops before aliases and the Release.
- **Release tooling comes from a TRUSTED ref, never from the tagged tree** — on a tag push the checkout IS the tagged commit, so `validate` would otherwise run the very script that decides whether that tag may be released. Both `validate` and `publish` check the tooling out separately (`github.ref` on a dispatch, the DEFAULT BRANCH on a tag push). **Do not overclaim this**: GitHub reads `release.yml` itself from the tag ref, so whoever can create a `v*` tag can supply their own workflow. The real boundary is the maintainer-only `v*` tag ruleset plus branch protection; this pipeline is the correctness gate inside it.
- **Every third-party action is pinned to a full commit SHA with its upstream tag in a comment** (`scripts/lib/actionPins.test.ts` globs `.github/workflows/` and fails on a floating ref, a short SHA, a missing version comment, or one action pinned to two SHAs). Runbook + partial-failure recovery: `docs/releasing.md`.

`db:seed` is a DEV-ONLY tool with an anonymized demo dataset. Never run it against data you care about. It ATTACHES the demo budget to the first existing user, so the dev/E2E flow is: register → `bun run db:seed` → the account sees the demo data. An empty start needs no tooling at all (fresh DB = empty budget → onboarding).

## Tests
- **The root command contract is the single source of truth — CI keeps NO second list.** `bun run verify` (= `typecheck` + `lint` + `test` + `build` + `policy:sources`) is the offline developer gate; `bun run verify:ci` (= `typecheck` + `lint:ci` + `test:db` + `build` + `policy:sources` + `security:audit`) is what `.github/workflows/ci.yml` invokes, and the Docker job depends on it. Add a phase by editing root `package.json`, never the workflow. `build` is NOT just `build:web` any more: it also runs `scripts/check-web-bundle.ts`, the §3f initial-JS budget (≤500,000 raw / ≤167,312 gzip bytes over the manifest's static-import closure) — so every gate that builds also enforces the size ceiling, and release verification cannot bypass it.
- **Format/lint is Biome, pinned exactly (root `biome.json`), with a lefthook pre-commit hook — and NOTHING mutates in a hook.** `bun run format` is the only writer; `lint`/`lint:ci` are non-mutating and part of verify/verify:ci, so `git commit --no-verify` cannot bypass the gate. Root `prepare` runs `scripts/install-hooks.ts`: with no `.git` (Docker build contexts — the Dockerfile COPYies this one script before each `bun install` precisely because bun runs `prepare` there) it skips cleanly; in a checkout (`.git` dir OR worktree `.git` file) it installs the pre-commit hook = NUL-safe staged Biome (`scripts/check-staged.ts` — argument arrays end to end, `./`-prefixed paths, never lefthook's `{staged_files}` templates) then full `typecheck`, sequential, no re-staging, NO pre-push hook. Disabled rules are deliberate and documented in CONTRIBUTING.md (behavioral fixes deferred: exhaustive-deps, array-index keys, button types + a11y cluster, non-null assertions, useTemplate); do not re-enable one casually and do not "fix" its findings inside an unrelated PR. The i18n extractor is layout-independent (whole-file matcher) — but editing an English string still changes its key: run `i18n:extract` after copy changes, not after pure formatting.
- **`policy:sources`** (`scripts/check-sources.ts` + pure rules in `scripts/lib/sourcePolicy.ts`) is a narrow SOURCE-TEXT gate over the files a self-hoster copies from (`README.md`, `compose.selfhost.yml`, `.env.selfhost.example`, `docs/install.md`, `docs/hosting.md`, `docs/operations.md`) plus `scripts/deploy.sh`: every Enveo image reference is bare or `:latest` — a numeric tag, an `X.Y.Z` placeholder or a digest is rejected THERE, while release tooling, tests and `docs/releasing.md` name exact versions freely — and the bootstrap script contains no remote download, pipe-into-a-shell or package-manager call. It NEVER queries GHCR: a documentation gate that asked the registry for the current version would fail on a network blip and would make the docs' correctness a property of the registry instead of the repository.
- **Unit/property**: `bun run test` — shared, API, web/lib and `scripts/`. These guard the core invariant (§ Domain invariants), carry-over semantics, FK-cascade parity between client and server, and replay idempotency.
- **`scripts/run-tests.ts` owns the child environment, and a shell prefix is NOT a substitute.** bun auto-loads `.env`, so `test` FORCES `OPENAI_API_KEY=""` and `TEST_DATABASE_URL=""` (DB groups skip); `test:db` forces the key empty but keeps an explicitly supplied `TEST_DATABASE_URL`. Tests exercising "no AI key" paths therefore pass for the right reason. The child is stamped `ENVEO_TEST_RUNNER`/`ENVEO_TEST_MODE`, and `scripts/lib/runner-contract.test.ts` asserts the delivered environment from inside it.
- **`test:db` is the last line of defence for real data — the per-suite fuses cannot fire.** Both modes overwrite the child's `DATABASE_URL` with an unroutable sentinel (route tests exercise real handlers through the POOLED db, and `resolveDatabaseUrl()` falls back to `localhost:5432/enveo` — a LIVE database on dev and self-host machines), which also disables the suites' own `TEST_URL === DATABASE_URL` checks. So `test:db` refuses to start unless `TEST_DATABASE_URL` is non-empty, `ENVEO_TEST_DB_ACK=throwaway` is set, it differs from `DATABASE_URL` **and** — unconditionally, because `.env.example` ships `DATABASE_URL` COMMENTED OUT — it is not the default application target. Comparison is on a canonical `host:port/database` where `localhost`/`127.0.0.1`/`::1`/`0.0.0.0` collapse to one token: a different spelling, user or password is NOT a different database.
- **`typecheck` is load-bearing, not cosmetic**: it runs shared, API, web app, web tests and `tsconfig.scripts.json`. Compile-time guards (e.g. `_rejectPooledDbAtCompileTime`, the `@ts-expect-error` canary that stops the pooled `db` reaching `withOperationLockInTx`) are enforced by NOTHING else — `bun test` strips types.
- **`security:audit`** (`scripts/audit.ts` + `security/audit-policy.json`) evaluates full `bun audit --json` and FAILS CLOSED: `bun` exits 1 both for real findings and for a registry failure, so the body must parse — and exit 1 with a body of ZERO advisories is itself treated as a failed scan (that contradiction is exactly what a degraded registry produces, and with an empty policy nothing else would catch it). Critical/high have no exception path; moderate/low need an exact, unexpired, reviewed entry (advisory id, package, range, and the installed version/dependency path resolved from `bun.lock`). Unknown, expired, stale, re-rated or moved findings fail; `addedOn` may not be in the future and the 90-day cap is measured from the EARLIER of `addedOn`/today. Never suppress with `bun audit --ignore`/`--audit-level` — accepted items stay visible in the table.
- **E2E**: drive a THROWAWAY stack only — fresh Postgres container, API with `WEB_DIST` pointing at the built web assets, headless Chromium via CDP. Never point E2E at a database you care about. Prefer prod-like serving (built assets, not the dev server): CSP and PWA behavior only show up there.

## Domain invariants
- Amounts are ALWAYS integer minor units (never floats), 1/100 of the major unit — hence only **2-decimal currencies** may be offered (see § Conventions). `Transaction.amount` is a positive magnitude; direction comes from `type` (expense/income/transfer) + `isRefund`. `month` = 'YYYY-MM', `date` = 'YYYY-MM-DD'.
- Account balances and envelope "available" are DERIVED from the ledger (`computeBudgetState`/`stateResponse`) — never materialize a balance column (property tests will break).
- Core invariant: Σ(available) + toBeBudgeted = Σ(on-budget account balances). Carry-over: negative available carries into the next month as a negative carry-in (no floor at 0).
- Local-first: the UI boots from the IndexedDB replica; a write = applyOp on the mirror + outbox → sync push/pull. The server-side `changes` journal is driven by Postgres TRIGGERS (so imports and FK cascades are captured too), not by route handlers. Conflicts are LWW per entity, delete wins; recovery = snapshot resync. `applyOp` must mirror FK cascades faithfully or replay loses idempotency.
- New mutation ops require FULL parity: zod schema (`shared/ops.ts`) + `applyOp` reducer + server push handler (`api/routes/sync.ts`) + replay/idempotency tests. Mirror FK behavior from the REAL schema (e.g. `transactions.envelope_id` is `set null`).
- **Operation lock** (`api/src/db/operationLock.ts`): cross-process serialization of one-shot initializers — a typed `(operation, id)` key from the central `OPERATION_LOCK` registry, mapped INSIDE Postgres to one `pg_advisory_xact_lock` (`hashtextextended` over a versioned canonical JSON string; the expression is private to the module). Callback+transaction API only: `withOperationLock` (own transaction, lock is the first statement) / `withOperationLockInTx` (caller's transaction — typed `DbTransaction`, the pooled `db` is rejected at compile time; the lock lives until the OUTER commit). One key per call, blocking semantics, short DB work only. First consumer: lazy initial-budget creation in `getBudgetId` (`budget.ensure-initial`, id = userId) — only the EMPTY case locks (re-check under the lock, insert at most one neutral budget); multiple budgets per user stay valid (NO `UNIQUE(budgets.user_id)`), and any future "first/default budget" path must reuse this key. **LOCK ORDER RULE**: creating a budget fires `log_change()` (SHARED changes-cursor lock), so any route holding the EXCLUSIVE changes-cursor lock (snapshot/pull/replace) must ensure the initial budget via the standalone lock path BEFORE its barrier transaction and resolve only an EXISTING budget inside it (`requireExistingTier`; `BudgetVanished` retries the ensure→barrier sequence, bounded) — never lazy-create under the exclusive changes lock (deadlock). `lockChangesCursor` stays the FIRST statement of its transaction. The signup gate (`auth.ts`) and `lockChangesCursor` keep their own dedicated protocols — do not migrate either onto the generic lock.
- E2EE: budgets have tier plain|e2ee + epoch + **cipherVersion 1|2**; v1 data routes require plain, sync2 requires e2ee (409 tier_mismatch) — new data routes MUST call requireTier. E2EE crypto lives ONLY in `web/lib/crypto.ts` (the server never encrypts E2EE data; it validates the `v2.` prefix and stays blind to AAD semantics). The separate server-side credential vault encrypts Own OpenAI keys only for plain budgets. The client keeps the DEK in IDB meta; the outbox stays plaintext and encryption happens only at push time (pending ops survive tier flips). Any 409 tier_mismatch → hard engine re-bootstrap (update tier meta from the body, reset cursor, re-boot; missing DEK → Unlock screen).
  - **Ciphertext format v2 (AAD)**: every op/checkpoint/key-envelope/budget-secret value is `"v2." + b64(nonce ∥ ct ∥ tag)` with MANDATORY AES-GCM additionalData — the UTF-8 `JSON.stringify` of one fixed tuple: op `["enveo-e2ee",2,"op",budgetId,epoch,opId]`, snapshot `[…,"snapshot",budgetId,epoch,uptoSeq]`, dek-wrap `[…,"dek-wrap",budgetId,epoch]`, budget secret `[…,"budget-secret",budgetId,epoch,"openai"]`. WHAT IS AUTHENTICATED: the op's identity (a valid ciphertext re-paired with another op's clear opId, budget or epoch fails), the checkpoint's claimed position (blob ↔ uptoSeq/epoch/budget), the key envelope's generation, and a budget secret's kind/budget/epoch. **NOT authenticated: the server-assigned journal ORDER** — Postgres allocates `seq` after the client encrypted, so `seq` is deliberately absent from the op AAD; never claim order authentication in code, docs or tests. Tuple builders and the encoder live only in `crypto.ts`; every API takes a mandatory typed context (no empty-AAD overload), decryption context comes from CALLER-expected values, and `v1.` is refused with `legacy_ciphertext` (no read fallback), malformed input with `bad_ciphertext`.
  - **Password rewrap ≠ data-key rotation**: `/sync2/rekey` (password change) rewraps the SAME DEK under the SAME epoch — ciphertexts stay valid. The mandatory **v1→v2 upgrade ceremony** (`POST /budget/e2ee/upgrade-v2` + `upgradeServerE2eeV2` in `web/lib/sync.ts`) is a REAL rotation: fresh DEK/salt/KEK, epoch+1, the proven LOCAL replica becomes the new checkpoint at uptoSeq 0, and one server transaction (budget row `FOR UPDATE`) swaps envelope + cipher_version + epoch, DELETES the whole legacy journal and replaces the checkpoint — idempotent for a retry of the same committed attempt, stale-epoch 409 otherwise. Old pairing codes and DEKs die with it; other devices re-unlock with the new password.
  - **Fail-closed legacy handling**: every normal sync2 route (reads included) answers a format-1 budget with 409 `{error:"e2ee_upgrade_required", tier, epoch, cipherVersion:1, budgetId}` before any write; the client stops the cycle (outbox/replica/cursor untouched), records the format and routes the human to the upgrade (Unlock's upgrade state / Settings → Privacy). NEVER flip `budgets.cipher_version` via SQL — that labels unauthenticated ciphertext as v2 without rotating the DEK (migration 0021 marks pre-existing e2ee rows as 1 exactly once). Deploy preflight for this change: `SELECT id, user_id, epoch FROM budgets WHERE tier='e2ee'` must be EMPTY on a plain-tier production; a non-empty result means back up and run the deliberate upgrade from a trusted local replica.

### Multi-tenant guard (load-bearing — do NOT weaken)
Accounts are mandatory and a persistent replica can outlive an expired/replaced session, so one browser may still contain user A's ledger + queued ops while a user B session appears. Explicit in-app sign-out is different: after pending-write recovery it ends the session and removes that account's local replica and key material. The session cookie is shared by every tab and can also be swapped MID-CYCLE (a sign-out+sign-in in another tab; the long-lived tab never sees a 401). One cycle makes many server writes, and the server's FK guards only reject references to another budget's EXISTING rows — fresh creates would sail into B's budget. Hence three layers (`web/lib/sync.ts`, "Account identity of the replica"):
- **Stamp**: the replica is stamped with the session userId (IDB meta). Boot does not hand the replica to the UI until the stamp is compared (`bootOwnerOk`); every CYCLE re-reads the session (`ensureIdentity` — only a verdict for the SAME user id is reused; memoizing per page load is a BUG we already fixed).
- **Outside explicit sign-out, only a STAMP MISMATCH may wipe** — via the human on SELFHOST (BootStatus `foreign` → ForeignReplicaScreen: export a backup / remove and continue), SILENTLY on CLOUD (`enterForeignReplica` discards the previous account's replica + outbox and reloads — the server is the durable copy there and exposing "another account's data is here" to a shared computer is itself a leak; unknown deployment fails safe to the screen). An UNSTAMPED replica whose ownership cannot be proven (`proveOwnership`) is UNPROVEN, not foreign: it refuses every server write (push, `/sync/replace`, `/sync2/reset`, e2ee enable/disable/rekey, checkpoint upload) and is NEVER destroyed. On selfhost nothing is destroyed unattended — the replica may be the last copy, and a user id does not survive a server rebuild.
- **Per-REQUEST tenant assertion on EVERY server write** (the authoritative layer — the client's check is one request older than the write): pushes NAME the budget they are for (`budgetAssertionFails`), the full-budget OVERWRITE routes NAME the user the client just verified (`ownerAssertionFails` — the tenant there is the USER, because a restore deliberately carries the BACKUP FILE's budgetId). Mismatch → 409 `{error:"budget_mismatch"}` BEFORE anything is written; the client re-proves and writes nothing. Any NEW write endpoint must carry one of these assertions.
- **PITFALL — `budgetId` is an EPOCH marker, not a tenant id**: lazy budget creation, wipe+reseed and a DB restore all mint a new one. It may NEVER be used alone to conclude "different account" (that false positive IS the 2.0 upgrade path: an unstamped 1.x replica of B_old vs. the freshly lazy-created empty B_new). A differing budgetId means "resync / cannot prove", not "foreign".
- **Device persistence**: one Login checkbox drives BOTH persistence layers — private device = persistent cookie (`rememberMe`) + IDB replica; shared device = session cookie + memory-only replica (`storageMode()` "memory-session"). After the choice, IndexedDB is never opened for account data in a shared-device session — a previous user's replica is neither read nor destroyed and the session never hits ForeignReplica (the first PRE-LOGIN boot on a fresh device may create the empty IDB schema + clientId before any choice exists; no user data reaches it). The canonical flag is `enveo.deviceStoragePolicy` (`persistent|session`; absent = persistent for upgrade compatibility); `enveo.deviceTrust` is read only for one-time migration. Explicit sign-out in either deployment flushes pending writes or requires a recovery choice, ends the session, and clears the current account's replica, DEK and legacy credential material. Google OAuth still has a persistent cookie limitation; the UI warns shared-device users to sign out.

## AI features
- Provider: OpenAI (`OPENAI_API_KEY`/`OPENAI_MODEL`; default model `gpt-5.6-luna`). No key → the **budget assistant** falls back to local rules; **screenshot import is AI-ONLY** (no key ⇒ 503 `ai_unavailable`). Quick-add (natural-language transaction entry) is GONE for good — UI removed in 3.1, its rule-based parser (unlocalizable PL/EN word tables) in 2.2.0, its API route in 3.5; do not re-introduce a rules path for entry.
- **ONE metered operator transport** (`api/src/aiSpend/transport.ts`) is the ONLY path to `openAiChatFetch` — a source gate fails the suite on any other reference. On **cloud** (open registration + operator key — `operatorAiSpendLimited` next to `signupsOpen`) every upstream ATTEMPT is check-then-record against `ai_user_monthly_spend` (migration 0020): ~$5 = `5_000_000_000` nanoUsd per user per UTC calendar month (a cloud-v1 CONSTANT, no env var), integer nano-USD bigints end to end, prices from the versioned registry (`aiSpend/pricing.ts` — cloud boot refuses an unpriced `OPENAI_MODEL`). NO reservations/predicted costs/reconciliation — deny only when RECORDED spend ≥ threshold; a successful answer's actual usage-derived cost is added afterwards (overshoot accepted); every failure (timeout, non-2xx, bad usage, unknown model, counter error) charges nothing, and the counter is FAIL-OPEN — it never blocks or degrades an AI answer. Denial contract: 429 `{error:"ai_budget_exhausted", retryAfterSeconds}` + `Retry-After` from the proxies; a durable import job turns `SpendDenied` into a scheduled retry at `Retry-After` (per window in cycle one); suggest denial → local rules. The interactive operator routes `/import/extract` and `/import/recognize` were removed in 4.3.0. Selfhost (closed OR `ALLOW_SIGNUPS=1`) bypasses the counter entirely — the docs carry the open-signups warning instead. Never reveal recorded spend. `AI_SAFETY_IDENTIFIER_SECRET` (optional, DEDICATED — never the auth secret) enables an HMAC `safety_identifier` on operator calls; raw user ids never go to OpenAI.
- Prompts live ONLY in `shared/aiPrompts.ts` — server and BYOK build identical requests from the same code (parity guarded by prompt-identity tests). Every prompt takes the UI locale (`AiLocale` = any BCP-47 tag) and the model answers in that language (envelope names, notes, rationales) — omitted ⇒ English.
- AI provider/model/custom profiles are budget preferences (`BudgetPreferences`) and follow the budget across devices; dashboard widget layout is budget-scoped too. Language/theme/accent are revisioned account preferences, while discreet mode is device-only. Providers: **rules** (default; local deterministic suggestions, zero egress), **Enveo AI** (operator key through Enveo), and **Own OpenAI**. For a plain budget Own OpenAI is envelope-encrypted in the server vault and requests flow browser → Enveo → OpenAI; for an unlocked E2EE budget the server stores only DEK-encrypted ciphertext and requests flow browser → OpenAI directly. The plaintext BYOK credential is never persisted in new client settings or returned by a read endpoint.
- Structured output uses strict `json_schema` (object root — wrap arrays in `{items}`). `reasoning_effort` is gated by `supportsReasoningEffort` and the enum stops at `low` (some models reject `minimal`).
- **Screenshot import reads up to 30 screenshots per job in WINDOWS of 6, in parallel** (`shared/importChunks.ts`; the 6 was never an OpenAI limit — the API takes 1,500 images per request — but cycle one's OUTPUT tokens grow linearly with screenshots and one 30-image request would blow the vision timeout all-or-nothing). Each window is its own cycle-one request with its own retry budget (`import_job_chunks` on the server, `chunkCiphertext` in the E2EE runner), its checkpoint releases only that window's screenshots, and a job of ≤6 keeps the model's raw rowIds so the corpus baseline is unchanged; multi-window rows are namespaced `c<window>:<rowId>`. Cross-window overlap the model cannot see is rebuilt after the merge: identical text is already declined by `reconcileImportProposals`, same date/amount/currency/direction with DIFFERENT text goes to ONE text-only seam call (`buildImportSeamPrompt`, ≤40 pairs, verdict ⇒ `duplicate_of`); a failed or capped seam becomes the `possible_duplicate` review reason, persisted as `result.seam` so a checkpoint resume flags the same rows. Cycle two is one call per job, batched above 80 rows. A window that exhausts its attempts does not fail the job: the result goes `ready` and its unread screenshots move — in the same transaction — into a new FAILED child job (`partialFailure.retryJobId`, images moved by position, ordinary `/retry`), so a ready job still never holds images. `saveExtraction` restarts `attempt` at 1: extraction and the post-extraction stage have separate retry budgets. Every upstream call logs `{jobId, stage, chunk, durationMs, promptTokens, completionTokens}` and nothing else; the eval harness records the same `telemetry` — that is the only evidence for ever changing `IMPORT_JOB_CHUNK_SIZE`.

## Auth (accounts are MANDATORY — since 2.0)
- better-auth is ALWAYS instantiated (email+password always enabled; Google only when `GOOGLE_CLIENT_ID`/`SECRET` are set). There is no no-auth mode — `AUTH_MODE`/`DEV_LOGIN` no longer exist. `BETTER_AUTH_SECRET` (≥32 chars) is REQUIRED: `assertAuthEnv()` fails the boot without it.
- Deployment profiles: `DEPLOYMENT=selfhost` (default) closes registration once a credentialed user exists; `DEPLOYMENT=cloud` keeps it open; `ALLOW_SIGNUPS=1` reopens it on selfhost. The policy is the pure `signupsOpen()` (`api/src/authPolicy.ts`) and is enforced SERVER-SIDE in better-auth's user-create hook (403 `signups_closed`) — never in the UI. "Credentialed" = has an `auth_accounts` row, so a pre-2.0 stub owner still reads as first-run (that IS the upgrade path).
- The gate takes a Postgres ADVISORY LOCK (`pg_advisory_xact_lock`, one reserved connection via `sql.begin`) around check+create, so two concurrent first registrations cannot both become "the first account". Never move that check onto the pooled `db` — lock and unlock would land on different sessions.
- `GET /api/auth/meta` (public, `{signupsOpen, firstRun, providers, deployment}` — leak nothing else) tells the Login screen what to render; `deployment` drives the device-trust checkbox default (selfhost → checked, cloud → unchecked). It MUST stay registered BEFORE the `/api/auth/*` wildcard: Hono matches in registration order.
- The session middleware protects ALL `/api/*` except `/api/auth/*` and `/api/health` (the AI proxy included). Budgets are lazily created per user (empty → onboarding wizard). E2E and tests sign up via `POST /api/auth/sign-up/email` (always available; the first sign-up on a fresh DB always succeeds).
- Lost password on selfhost (no email infra): `bun run auth:reset-password <email> <new-password>` on the server.
- Auth tables are `auth_sessions`/`auth_accounts`/`auth_verifications` (+ extended `users`) — do NOT confuse `auth_accounts` with the domain `accounts` table (bank accounts).

## Conventions
- Code, comments, tests, and commit messages in **English**. Conventional Commits with scope: `feat(api):`, `fix(web):`, `chore:`.
- **i18n is message-as-key: the ENGLISH SENTENCE IS THE KEY** — `t("Transactions")`, `tp("{n} change | {n} changes", n)`. There is NO English dictionary: with `en`, `t()` returns its argument, so a missing translation degrades to correct English (that is what makes partial community translations shippable). A locale is ONE file in `web/src/lib/i18n/locales/` (`Partial<Record<Message, string | PluralForms>>`) plus ONE line in `i18n/registry.ts` (lazy `import()`, endonym, `community` flag). Plurals come from `Intl.PluralRules` — the required CLDR categories per language are COMPUTED, never hand-written, and the English source carries both forms joined by `" | "`. Strings outside a `t()` call (code→text maps, ternaries) are wrapped in `msg("…")` so the extractor sees them. Keep every message a WHOLE phrase — gluing fragments in JSX forces English word order on every other language (the tests reject fragments).
  - `bun run i18n:extract` (in `packages/web`) regenerates `i18n/messages.generated.ts` — the `Message` union, so a typo at a call site is still a compile error. `i18n.test.ts` fails on orphans, missing plural categories and dropped `{placeholders}`; `bun run i18n:ambiguity` lists short messages with their call sites (the "Type" verb/noun trap).
  - **PITFALL — editing an English string CHANGES ITS KEY and silently orphans every translation of it.** Run `bun run i18n:extract` and READ the orphan report before shipping a copy change; the orphans name exactly what must be re-translated.
- Money is formatted via `M()`/`formatMoney` — never hardcode a currency symbol in JSX. **Only 2-decimal currencies may be offered** (`SUPPORTED_CURRENCIES`, ~31 codes): the ledger is integer 1/100 minor units end to end, so a 0-decimal (JPY, HUF, ISK…) or 3-decimal (KWD, BHD) currency would render and parse every amount 100×/10× off. `CURRENCY_DIGITS` is PINNED from CLDR and `currency.test.ts` checks the list against it — deliberately NOT against the runtime's `Intl`, whose ICU lags CLDR by years (bun 1.3/ICU 75 still calls HUF/COP/IDR 2-decimal; current browsers say 0).
- Colors: accent/danger/CTA are CSS variables; in SVG set them via `style` (presentation attributes don't resolve `var()`); use precomputed alpha variables — never string-concatenate alpha onto a color.

## Known pitfalls (hard-won — do not rediscover)
- `workbox-window` MUST be in `dependencies` of packages/web (pulled by `virtual:pwa-register`), or the frozen-lockfile Docker build fails.
- A CSS `transform` on an ancestor breaks `position: fixed` descendants. Sheets animate with transforms — render fixed overlays (pads, full-screen editors, nested pickers) via `createPortal(document.body)`.
- CSP is `script-src 'self'` (no unsafe-eval) — the amount calculator uses a hand-written arithmetic evaluator (`evalArith`); keep it eval-free.
- WebKit/iOS can drop hit-testing on a composited (transformed) layer after unmounting a full-screen fixed overlay above it — force a compositing rebuild after closing such overlays (see the opacity-kick pattern in ImportSheet).
- Reading DOM state (e.g. `aria-checked`) synchronously right after `.click()` observes the pre-render value — React batches; wait a tick in tests.
- PWA update detection is byte-based on `sw.js` (new asset hashes), not version-number based; `APP_VERSION` in `version.ts` is manual semver — bump it on every user-visible change. The update banner can't be tested against the dev server (SW off).
- **A field added in version N does NOT exist in every replica row — and a fresh `db:seed` can never show you that.** The IndexedDB replica is long-lived and updated by OPS, not refetched: an entity written before the field existed keeps NO key for it (only rows touched since carry an explicit `null`), so the property reads back `undefined` and every `!== null` check treats it as SET. `automaticEnvelopeId` (3.8) did exactly this on a device whose accounts predate it: `linkedEnvelope()` returned `undefined`, so a transfer between two UNLINKED accounts offered the automatic-envelope switch and previewed "no envelope change" (`from === to`, both `undefined`). Normalise with `?? null` at the DOMAIN boundary — the one function every consumer already goes through — never at each call site, and pin it with a test whose fixture `delete`s the key. The same holds for stored transactions (`allocation*EnvelopeId`) and for any future column: assume the oldest client shape, not the newest snapshot.
- `source_ref` (screenshot-import metadata) is part of `ClientLedger` and survives sync, `/api/sync/replace` and JSON export. Keep it replicated: E2EE screenshot-import dedupe and correction learning run locally and depend on it.
- `.git` is in `.dockerignore` → `__BUILD_INFO__.sha` is empty in a container build UNLESS `--build-arg SOURCE_COMMIT=<sha>` is passed (the release workflow does; a plain local `docker build` does not, and then only the build timestamp shows).
- `.dockerignore` excludes `**/*.test.ts` — the runtime stage copies whole source directories, so without it the 28 test files living next to `packages/api/src` / `packages/shared/src` would ship to users. Never `COPY` a source tree into the image without checking what else lives in it.
